# Spec: KnowledgeBase bounded context — change `knowledge-bases`

Tenant root for Shiori. Every Knowledge Base is an isolated container
authenticated by its own API key. Future contexts (`documents`, `retrieval`)
scope their data to a `knowledgeBaseId` resolved by this context's guard.

---

## 1. Domain Model

### 1.1 KnowledgeBaseAggregate

| Field | Type | Nullable | Notes |
|-------|------|----------|-------|
| id | UUID | No | Generated on create |
| name | string | No | 1–100 chars |
| description | string | Yes | Max 2000 chars |
| apiKeyHash | string | No | SHA-256 hex digest (64 chars) of the current active key |
| createdAt | Date | No | Set on create |
| updatedAt | Date | No | Set on every write |

### 1.2 Business Rules

- `name` MUST be non-empty and at most 100 characters.
- `description`, when provided, MUST be at most 2000 characters.
- `apiKeyHash` MUST be a 64-character lowercase hex string (SHA-256 digest).
  Any other shape MUST be rejected with a domain validation error
  (`InvalidKnowledgeBaseApiKeyHashException`).
- The plaintext API key is generated by `GenerateApiKeyService`, is NEVER
  persisted, and is returned to the caller exactly twice in the aggregate's
  lifetime: once on `CreateKnowledgeBase`, once per `RotateKnowledgeBaseApiKey`
  call. It cannot be retrieved afterward by any query.
- Rotating the API key invalidates the previous key immediately — there is no
  overlap window where both keys are valid.
- A knowledge base has exactly one active API key at a time (no multi-key
  support in this change).

### 1.3 Domain Events

| Event | Trigger | Payload |
|-------|---------|---------|
| `KnowledgeBaseCreated` | After successful create | `{ id, name }` |
| `KnowledgeBaseUpdated` | After successful update | `{ id, name }` |
| `KnowledgeBaseDeleted` | After successful delete | `{ id, name }` — future `documents`/`retrieval` cascade hook |
| `KnowledgeBaseApiKeyRotated` | After successful rotation | `{ id, name }` — MUST NOT include the key or its hash |

## 2. Repositories

### 2.1 IKnowledgeBaseWriteRepository

MUST expose:
- `save(kb: KnowledgeBaseAggregate): Promise<void>`
- `findById(id: string): Promise<KnowledgeBaseAggregate | null>`
- `delete(id: string): Promise<void>`

### 2.2 IKnowledgeBaseReadRepository

MUST expose:
- `findById(id: string): Promise<KnowledgeBaseViewModel | null>`
- `findByApiKeyHash(hash: string): Promise<KnowledgeBaseViewModel | null>`

Neither repository is tenant-scoped by `createTenantRepository` — a
knowledge base is the tenant root itself (see `design.md`).

**This context intentionally has no `findByCriteria` query or repository
method.** See §5 below.

---

## 3. Commands

### 3.1 CreateKnowledgeBase

**Inputs:** `name` (required), `description?`.

**Rules:**
- No authentication required — this is the tenant-creation ("signup") entry
  point. There is no existing API key to authenticate with yet.
- Generates a new API key (`GenerateApiKeyService`), hashes it
  (`HashApiKeyService`), persists only the hash.
- Response MUST include the plaintext key. This is the only command/query in
  this context whose response includes the plaintext key alongside `create`
  itself (`RotateKnowledgeBaseApiKey` also does, per §3.4).

### 3.2 UpdateKnowledgeBase

**Inputs:** `id` (from authenticated context, not client input), partial
`{ name?, description? }`.

**Rules:**
- Requires a valid `X-API-Key` (`KnowledgeBaseApiKeyGuard`).
- Knowledge base MUST exist (404 otherwise — unreachable in practice since
  the guard already resolved it, but the assert service still guards the
  invariant).
- Partial update: unset fields are preserved.

### 3.3 DeleteKnowledgeBase

**Inputs:** `id` (from authenticated context).

**Rules:**
- Requires a valid `X-API-Key`.
- After deletion, the same API key MUST NOT authenticate any further request
  (`findByApiKeyHash` returns null) — the guard then responds 401, not 404,
  since from the caller's perspective the credential itself is now invalid.

### 3.4 RotateKnowledgeBaseApiKey

**Inputs:** `id` (from authenticated context).

**Rules:**
- Requires a valid `X-API-Key` (the *current* one).
- Generates a new key + hash, replaces `apiKeyHash` on the aggregate.
- The previous key MUST stop authenticating immediately after this command
  completes.
- Response MUST include the new plaintext key. It is never retrievable again
  after this response.

---

## 4. Queries

### 4.1 KnowledgeBaseFindById

**Inputs:** `id` (from authenticated context — never a client-supplied path
param or GraphQL argument; see §5).

Returns the caller's own `KnowledgeBaseViewModel`, with `apiKeyHash` stripped
by the transport mapper before serialization.

### 4.2 KnowledgeBaseFindByApiKeyHash

**Inputs:** `hash`.

Internal-only query — no REST/GraphQL/MCP surface. Used exclusively by
`KnowledgeBaseApiKeyGuard` to resolve the `X-API-Key` header to a tenant.
Returns `KnowledgeBaseViewModel | null`.

---

## 5. Authentication & Guard Behavior

### 5.1 KnowledgeBaseApiKeyGuard

- Reads the `X-API-Key` header (HTTP and GraphQL execution contexts both
  supported, same dual-context resolution pattern as gardenia's
  `SpaceGuard`).
- Routes/resolvers annotated `@SkipKnowledgeBaseAuth()` bypass the guard
  entirely (used only by `CreateKnowledgeBase`).
- Missing header → `KnowledgeBaseUnauthorizedException` (401).
- Header present but no knowledge base matches its hash → same 401 (never
  reveal whether the failure was "no such key" vs. "malformed key" — both
  collapse to a generic unauthorized response).
- Valid key → sets `req.knowledgeBaseId` to the resolved id. Does NOT itself
  populate `KnowledgeBaseContext` — that is `KnowledgeBaseContextInterceptor`'s
  job (guards resolve before the handler executes; an ALS frame opened in a
  guard would close before the handler chain completes — see `design.md`).

### 5.2 Why no `:id` parameter anywhere

Every authenticated route in this context operates on "the knowledge base
identified by the caller's own API key" — there is no `GET
/knowledge-bases/:id`. This is a deliberate simplification over a
guard-resolves-A-but-param-requests-B confused-deputy check: removing the
parameter removes the bug class entirely, since there is nothing to
mismatch.

### 5.3 Why no cross-tenant `findByCriteria`

`openspec/config.yaml` marks the Criteria pattern "mandatory for every
context, no exception." This context is the deliberate, documented
exception: under API-key-only auth, no caller is authorized to see knowledge
bases other than their own, so a list query would either be trivially
useless (always 0 or 1 result) or a data-leak vector if ever miswired to
omit the tenant filter. If Shiori later grows an admin/root identity, a list
query belongs on that future admin-scoped context, not here.

## 6. Transport

### 6.1 REST endpoints (prefix: `api/knowledge-bases`)

| Method | Path | Guard | Description |
|--------|------|-------|-------------|
| POST | `/` | None (`@SkipKnowledgeBaseAuth()`) | Create; response includes plaintext `apiKey` |
| GET | `/me` | KnowledgeBaseApiKeyGuard | Get the caller's own knowledge base |
| PATCH | `/me` | KnowledgeBaseApiKeyGuard | Update name/description |
| DELETE | `/me` | KnowledgeBaseApiKeyGuard | Delete |
| POST | `/me/rotate-api-key` | KnowledgeBaseApiKeyGuard | Rotate; response includes new plaintext `apiKey` |

### 6.2 GraphQL operations

| Operation | Type | Guard | Description |
|-----------|------|-------|-------------|
| `createKnowledgeBase(input)` | Mutation | None | Create |
| `knowledgeBase` | Query | KnowledgeBaseApiKeyGuard | Self lookup, no arguments |
| `updateKnowledgeBase(input)` | Mutation | KnowledgeBaseApiKeyGuard | Update |
| `deleteKnowledgeBase` | Mutation | KnowledgeBaseApiKeyGuard | Delete → returns `Boolean` |
| `rotateKnowledgeBaseApiKey` | Mutation | KnowledgeBaseApiKeyGuard | Rotate |

### 6.3 MCP

None. See `proposal.md` Deviation 2 — every operation here is credential
lifecycle management, which `AGENTS.md` requires an explicit decision to
expose over MCP; this change makes that decision "not now."

## 7. Scenarios

### SC-01 Create — happy path
**Given** no prior state
**When** `POST /knowledge-bases {name: "Docs"}`
**Then** HTTP 201, response includes `id`, `name`, `createdAt`, and a
plaintext `apiKey` matching `^kb_[A-Za-z0-9_-]{43}$`; `KnowledgeBaseCreated`
event dispatched; the persisted row has no plaintext key anywhere.

### SC-02 Update — happy path
**Given** a knowledge base KB1 with API key K1
**When** the holder of K1 sends `PATCH /knowledge-bases/me {name: "Docs v2"}`
**Then** HTTP 200, `name` updated, `KnowledgeBaseUpdated` event dispatched.

### SC-03 Delete then re-authenticate
**Given** a knowledge base KB1 with API key K1
**When** the holder of K1 sends `DELETE /knowledge-bases/me`, then
`GET /knowledge-bases/me` with the same K1
**Then** the delete returns HTTP 200 (or 204); the subsequent GET returns
HTTP 401 (the key no longer resolves to any knowledge base — not 404).

### SC-04 Create bypasses the guard entirely
**Given** no `X-API-Key` header sent
**When** `POST /knowledge-bases {name: "Docs"}`
**Then** HTTP 201 — `KnowledgeBaseFindByApiKeyHashQuery` is never dispatched
for this route.

### SC-05 Update/Delete/Rotate on a knowledge base that no longer exists
**Given** KB1 was deleted
**When** any authenticated mutation is attempted with KB1's old key
**Then** HTTP 401 at the guard layer — the application layer's
`KnowledgeBaseNotFoundException` (404) is unreachable via transport in
practice, since the guard is the only path to a resolved `id` and it already
filters out unknown keys. It remains a defense-in-depth invariant in the
handler.

### SC-06 Unknown API key
**Given** a syntactically plausible but never-issued key
**When** any guarded route is called with `X-API-Key: <that key>`
**Then** HTTP 401.

### SC-07 Missing API key header
**Given** a guarded route
**When** called without an `X-API-Key` header
**Then** HTTP 401.

### SC-08 Valid key resolves the correct tenant
**Given** two knowledge bases KB1 (key K1) and KB2 (key K2)
**When** `GET /knowledge-bases/me` is called with `X-API-Key: K1`
**Then** the response is KB1's data, never KB2's; response contains no
`apiKeyHash` field.

### SC-09 GraphQL query accepts no id argument
**Given** the GraphQL schema for this context
**When** inspecting the `knowledgeBase` query's arguments
**Then** it accepts none — the resolved knowledge base comes exclusively
from `req.knowledgeBaseId` set by the guard.

### SC-10 Rotate invalidates the previous key immediately
**Given** a knowledge base KB1 with API key K1
**When** the holder calls `POST /knowledge-bases/me/rotate-api-key`
(authenticated with K1), receiving new key K2
**Then** the response includes K2; a subsequent request authenticated with
K1 returns HTTP 401; a request authenticated with K2 returns HTTP 200.

### SC-11 Tenant context ALS isolation
**Given** two concurrent requests, one resolved to KB1's `knowledgeBaseId`,
one to KB2's
**When** both are in flight simultaneously (`Promise.all`)
**Then** `KnowledgeBaseContext.get()` inside each request's async execution
chain returns only that request's own `knowledgeBaseId`, never the other's.

### SC-12 createTenantRepository injects the tenant id
**Given** a fake `Repository<E>` wrapped via `createTenantRepository`, with
`KnowledgeBaseContext` scoped to `knowledgeBaseId = "kb-1"`
**When** `find()`, `save()`, and `delete()` are called through the proxy
**Then** the underlying calls receive `knowledgeBaseId: "kb-1"` injected into
their `where`/entity/criteria respectively, without the caller having passed
it explicitly.
